### Fixed
- **Issue #397：planning 完整性檢查把共享工作樹的 `__pycache__` churn 誤判為 planner 汙染**：本機部署常見拓撲是 daemon 以 repo 為 `WorkingDirectory` 常駐、與 planning launcher 共用同一棵 operator 工作樹；daemon 對既有模組的 lazy import 會隨時在快照窗口內重編 `__pycache__/*.pyc`。`planning_runtime._tree_snapshot` 過去雜湊整棵樹只跳過 `.git`，把這種可重生的 bytecode churn 算進去，被 `_invoke_json` 的 operator 快照前後比對誤判成「planner 修改了 operator worktree」而 fail-closed 到整段 `raise ValueError` + rollback；`_copy_planning_sandbox` 的 `copytree` 也只 `ignore(".git")`，同一批 churn 還可能在複製途中造成 race read 例外。修法：`_tree_snapshot` 的目錄走訪加上 `__pycache__` 目錄（連同其下所有內容）與 `*.pyc` 檔名的跳過規則——CPython 的 `.pyc` 是 timestamp/hash-based 驗證（PEP 552），植入的孤兒 `.pyc` 不會被 import 採用，跳過雜湊不放寬既有 fail-closed（其他任何檔案異動仍會觸發 mismatch）；`_copy_planning_sandbox` 的 `ignore_patterns` 同步排除 `__pycache__`／`*.pyc`（sandbox 本就不需要 bytecode）。同時修正 `planning.py` `run_heterogeneous_brainstorm` 三處同型 `except Exception` 把底層例外壓平成單一字面值 reason（`question-pack-malformed`／`secondary-output-malformed`／`primary-integration-malformed`）的雙重誤導問題：改為 `except Exception as exc`，reason 併入 `f": {type(exc).__name__}: {str(exc)[:160]}"`，讓 #393 的 planning-failure evidence 與 `recover-planning` 的 `_read_planning_failure_record` 能直接看到底層例外（兩者皆只要求非空字串，不受影響）。新增回歸測試釘住雙向行為：`__pycache__`／`.pyc` churn（含巢狀套件目錄）不得觸發 mismatch，且 `_invoke_json` 整合層級也不得 raise；非 bytecode 檔案異動仍必須觸發 mismatch（fail-closed 保留）；三處 `except Exception` 皆透傳例外型別與訊息片段。修正前皆已確認 FAIL。
