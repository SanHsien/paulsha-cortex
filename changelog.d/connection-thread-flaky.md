### Fixed
- **Issue #445：`test_server_discards_finished_connection_threads` thread-timing flaky（連線執行緒已 `stopped` 但尚未從 `_connection_threads` list 移除）**：查證發現真正成因並非「斷言跑得比 discard 清理快」——該測試自建立起就已對 `_connection_threads == []` 加 1.0s 有界 poll（見 commit 94ea287），問題出在 `MonitorServer.serve_forever()`（`paulsha_cortex/monitor/server.py`）accept loop 內 `t.start()` 與「把 `t` 註冊進 `_connection_threads`」兩步順序反了，構成一個 TOCTOU race：連線處理執行緒若在 `t.start()` 呼叫後、accept loop 尚未取得 `_connection_threads_lock` 完成 append 前就已跑完（`_handle_connection` 處理 `list_projects` 這類簡單請求往往微秒等級完成），該執行緒自身 `finally` 區塊的 self-removal 會因「此時它根本還不在 list 裡」而形同無效；accept loop 隨後才把這條**已經死亡**的執行緒 append 進 list——由於沒有第 4 條連線觸發 accept loop 下一輪的 lazy `is_alive()` 過濾，這條殘留會永遠留在 `_connection_threads` 裡，任何長度的 poll 都等不到它消失。以決定性重現腳本驗證（monkeypatch `threading.Thread.start`：僅對 `_handle_connection` 目標的執行緒，在 `start()` 內部強制 `join()` 到底才返回，保證 accept loop 恢復執行時該執行緒必已 `stopped`，不靠排程運氣猜時序）：修復前每次執行皆重現與 CI 完全相同的失敗特徵（`_connection_threads` 內殘留一條 `<Thread(..., stopped daemon ...)>`，3 秒 poll 亦不消失）；修復後連跑 5 次皆收斂為 `[]`。修法：`serve_forever()` 的 accept loop 改為先在鎖保護下把 `t` append 進 `_connection_threads`、再呼叫 `t.start()`，讓執行緒不可能在被登記之前就結束（`_handle_connection` 的 self-removal 因而必定有效，關閉整個 race window，而非僅降低機率）；另同步把測試側既有的 poll 上限從 1.0s 提高到 2.0s（與同檔案其他等效 poll 的既有慣例看齊），作為純排程延遲的防禦餘裕層，非本次真正的修復點。回歸驗證：`test_server_discards_finished_connection_threads` 以 20 次獨立 subprocess 呼叫＋20 次同行程 in-process 呼叫共 40 次全綠；`tests/test_stage9_project_monitor_service.py` 整檔連跑 3 次（42 tests）全綠；全套 pytest：2362 passed、32 subtests passed（另有 2 個與本票無關的既有環境性失敗——本機 `/tmp/.git` 污染導致 `test_fix_dispatch_spec_path.py` 的 `_infer_repo_root` 相關 2 個測試紅，非本次變更引入）。
