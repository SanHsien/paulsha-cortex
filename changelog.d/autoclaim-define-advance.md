### Fixed
- **Issue #420：auto-claim 建立的 run 於 define 完成後永久卡住，periodic tick 不接手，explicit intake 卻能同步跑 define→plan→build**：`_claim_action`（`work_actions.py`）對「既有 ongoing run」的既有-run 分支（`work_actions.py:1611` 起）過去只在字面比對 `args.get("action") == "resume"`（即人工經 `cortex work resume` 觸發）時才重呼叫 `workflow_starter`——這是唯一能讓卡在 `apply_workflow_action(action="start")` 之 claim→define→plan 同步續推段中途被中斷（例如 `_load_planning_artifacts` 一類、未被任何 needs_human 分支接住的例外）的 run 重跑一次的路徑。periodic auto-claim scan（`run_auto_claim_scan`，daemon 每輪 tick 呼叫）固定帶 `args={"action": "auto-scan"}`，`automatic=True`，永遠不滿足這個字面比對；`decide_auto_claim` 對這種「facets 乾淨、`active_status=="ongoing"`」的既有 run 每輪都只會經 `_resume_decision` 判定 `action="resume"`，落到既有-run 分支後因條件不成立直接 `active = canonical_run.to_dict()` 原樣反映——`workflow_starter` 永遠不會再被呼叫，run 因此永久停在 `current_phase="define"`（facets 乾淨、零 job、`updated_at` 停滯），無 needs_human、無錯誤，觀測面全綠。explicit `cortex work intake`／`cortex work resume` 走同一個 `_claim_action`，但 `args["action"]` 分別命中 `decision.action == "claim"`（全新 claim，直接呼叫 `workflow_starter`）或字面 `"resume"`（既有 run 重試），所以能同步續推；auto-claim 建立的 run 兩者都命不中，成了無人接手的孤兒狀態。
  - **修復**：既有-run 分支的重試觸發條件新增 `automatic and decision.action == "resume"`（`work_actions.py:1638`），讓 periodic auto-claim scan 對自己建立的「ongoing、facets 乾淨、卡在 define」的 run 也能重呼叫 `workflow_starter`，等價於 explicit resume 已有的續推行為。刻意**不**擴及 `decision.action in {"needs_human", "blocked"}`：那兩類仍只在明確 `args["action"] == "resume"`（人工介入）時才重試，維持 #373 修復的守衛——auto-claim 不得自動清除或重試 needs_human run。`start_canonical_workflow` 對非 define phase 的既有 run 本就是原樣 early return（`existing_run.current_phase != "define"` 短路），故對 plan/build/verify/review 等已推進的 run 重呼叫 `workflow_starter` 是既有的安全 no-op，不受本次修復影響；與 #381 的 spawn admission、#383 的 dispatch_gate_scan 皆屬完全不同、更早的呼叫鏈（`start_canonical_workflow` 的 define 續推段本就不吃 `spawn_admission` 參數，也不經過 handoff manifest／registry 對帳），不衝突。
  - 新增 2 個回歸測試（`tests/test_work_actions.py`）：`test_periodic_auto_claim_scan_retries_run_stuck_at_define`（模擬一個 facets 乾淨、卡在 define 的 auto-claim run，periodic tick 後 `workflow_starter` 被重呼叫、run 推進到 plan）修正前已確認 RED（`workflow_starter` 從未被呼叫）；`test_periodic_auto_claim_scan_does_not_retry_needs_human_run`（同場景但 facets 帶 `needs_human`，斷言 `workflow_starter` 完全不得被呼叫，否則直接 `AssertionError`）驗證 #373 守衛不受影響，修正前後皆通過。全套 pytest：2313 passed、32 subtests passed（基線 2311/32，淨增 2）。
