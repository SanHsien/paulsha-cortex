### Fixed
- **Issue #373：authority-restart 每 tick 剝除 needs_human 並改寫 source_revision，claim_key 不更新導致永久重觸發**：完整迴圈——每個 daemon tick，`run_auto_claim_scan` 呼叫 `work_actions._claim_action`（`work_actions.py:1499-1502`）判定 `canonical_run.claim_key != _expected_claim_key(authority)` 且 `automatic=True` 即觸發 `registry._manager_reset_workflow_for_authority_restart`（`registry.py:1910-1967`）：改寫 `source_revision=authority_digest`、`attempts["verify"] += 1`、剝除 `needs_human` facet；同一 tick 內，`manager_daemon.py` 的 resume 迴圈（原 `:925`）唯一跳過條件只看 `"blocked" in facets`，不看 `needs_human`——needs_human 剛被剝除，於是放行進 `manager.resume_workflow_run`；後者對 needs_human 的 early-return（`operator_resume` 預設 `False`）此時同樣看不到 needs_human，繼續往下派工，撞上 `_job_for_workflow_card`（`manager.py:2606-2639`）比對到舊 job 的 `source_revision` 與 run 剛改寫的新值不符，raise `workflow job binding mismatch`；`manager_daemon.py` 的 except handler 把 `needs_human` 寫回；但 `claim_key` 從未在 reset 過程中被更新，故下一個 tick 第一步的觸發條件永久為真，迴圈無限重複（生產環境已累計 166k+ 筆同型 log）。
  - **根治（(a)）**：`registry._manager_reset_workflow_for_authority_restart` 現在會把 `claim_key` 同步重算為 `claim_key_for_authority_digest(repo, work_id, authority_digest)`（新增於 `claim.py`，由 `build_claim_key` 共用同一份雜湊公式，避免邏輯分岔）——reset 完成後 `claim_key` 立即與新 authority 對齊，下一個 tick 若 authority 沒有再變，`work_actions.py:1499-1502` 的觸發條件即為假，不再重複 reset；只有 authority 真的再前進時才會合法地再次觸發（authority-restart 屬合法的 authority 前進，非 abandon 後重宣告，claim_key 隨 authority_digest 同步演進不違反 #299 的『claim_key 唯一性僅約束 ongoing runs』不變式——同一 (repo, work_id) 在此路徑上全程只有一列 ongoing run 被原地 `replace`，不會與其他 ongoing run 的 claim_key 相撞）。
  - **縱深防禦（(c)）**：`manager_daemon.py` 的 resume 迴圈跳過條件新增 `"needs_human" in workflow.facets`，與 `manager.resume_workflow_run` 自身對 needs_human 的 early-return 契約對齊，避免已經 needs_human 的 run 被無謂送進 resume 流程。
  - 未採用方案 (b)（把 job 的 `source_revision` 排除於 binding 檢查之外，或 authority-restart 後主動 rebind／invalidate 舊 job）：fix (a) 已消除永久重觸發的根因，(b) 屬進一步放寬 binding 檢查的獨立議題，可能誤用已綁定到舊 authority digest 的 verify/review evidence，超出本次修復範圍。
  - 新增 3 個回歸測試：`tests/test_work_actions_retry_invalidation.py` 的 `test_authority_restart_reset_syncs_claim_key_to_new_authority`（reset 後 `claim_key` 必須等於新 authority 的 expected key）與 `test_repeated_automatic_scan_on_unchanged_authority_does_not_retrigger_restart`（模擬多次 daemon tick：同一 authority digest 下第二次起不得再觸發 restart、`needs_human` 不再被剝除、`attempts["verify"]` 不再累加）；`tests/test_manager_daemon_tick_isolation.py` 的 `test_periodic_tick_skips_needs_human_workflow_without_calling_resume`（已 needs_human 的 run 不得被送進 `resume_workflow_run`）。三項修正前皆已確認 FAIL（RED）：前二者因 `claim_key` 未同步而斷言失敗，後者因 resume 迴圈仍呼叫 `resume_workflow_run` 而斷言失敗；修正後全部轉綠，既有 authority-restart 測試（`test_authority_restart_invalidates_only_verify_and_review_preserving_build` 等）維持通過，未發現任何既有測試遷就此壞行為。
