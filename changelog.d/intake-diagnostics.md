### Fixed
- **Issue #389：work intake 對 issue-only work item 必然失敗，且錯誤訊息無法診斷**：lifecycle reducer（`monitor/lifecycle.py`）只在 `state == "todo" and confidence == "confirmed"` 時投影 `next_actions=("start",)`；只 link 一個 GitHub issue、沒有 todo-kind 來源（workstream `todo.md` path link 或 openspec change）的 work item 永遠停在 `topic`，拿不到 `start`。`coordinator/claim.py::_authority_from_canonical_row` 對這種 row 過去有三個獨立的 bare `return None` 出口（全 sources 皆 inferred／`next_actions` 無 `start` 且無 active workflow／confirmed sources 內無 todo-kind 來源），呼叫端（`_load_work_authorities_with_diagnostics`）只把它們當「這列不算」悄悄丟棄、不留任何診斷；`load_work_authority` 找不到目標也找不到 skip 診斷，只能落回與「row 根本不存在」「issue 被多個 work_id 認領」共用的泛化 `confirmed work authority missing or ambiguous`，operator 需要逆向工程 reducer 才知道缺什麼。三個出口改為各自 raise 專屬 `AuthorityValidationError`（新增 reason code `authority-all-inferred`／`authority-not-startable`／`authority-no-confirmed-todo-source`），訊息內含 work_id 與（若可取得）目前 lifecycle state，並指路「需要一個 active 的 Todo 來源」；`_load_work_authorities_with_diagnostics` 既有的 per-row isolation（#206）原樣接住這些例外存進 skipped diagnostics，`load_work_authorities()`（bulk 掃描）行為不變（skipped 本就被捨棄），只有 `load_work_authority()`（intake/start/resume 等 work-action 共用的目標查找）會浮現新訊息；真正的「row 不存在」與「issue 被多個 work_id 認領」兩種情境維持原有的泛化訊息，不被新分支吃掉。同步補文件：`docs/unified-work-lifecycle.md` 的 Intake 段落新增「只 link issue 不足以讓 work item 變成可 claim」說明；`cortex work --help`（`paulsha_cortex/cli.py` 的 `_WORK_HELP`，先前完全缺 `intake` 條目）新增 `intake` 說明與 claim 前置條件；`docs/onboarding/concepts.md` 補一句指向該前置條件的指標。新增 `tests/test_claim_authority_topic_diagnostics_389.py`（7 個回歸測試：三個新診斷分支、兩個「不得被吃掉」對照組、一個確認 diagnostic 訊息維持既有 AI-SEC-001 契約——`work_id` 在通過 identity 安全正規式前一律走 `_diagnostic_label` 而非嵌入原始值）與 CLI help 對齊測試，並修正 1 個既有測試（`test_work_claim.py` 的 `display-only` row 原本斷言泛化訊息，現改斷言 `authority-all-inferred` 專屬診斷）。修復前以新測試檔確認 RED（3 個新分支測試皆重現泛化 `missing or ambiguous`），修復後轉 GREEN。全套 pytest：2319 passed、32 subtests passed（基線 2311/32，淨增 8：7 個新測試＋1 個新 CLI help 測試）。
