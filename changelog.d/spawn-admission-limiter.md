### Fixed
- **Issue #381：fanout 同時啟動 N 個 builder 打爆 GitHub `/user` 端點配額，三個 builder 同一秒全部 `builder-failed`**：`autonomy.dispatch_ready`（fanout 迴圈，`autonomy.py:502` 起）與 workflow lane（`manager_daemon.py` periodic tick 的 resume 迴圈，`manager_daemon.py:930-980` 起，實際 spawn 點在 `manager._dispatch_workflow_card`）過去背靠背 spawn 全部就緒單位，無 sleep／gap／併發上限；copilot executor 每次啟動連續探測 GitHub `/user` 約 6-7 次驗證登入態，該 quota bucket 與 core rate_limit 分離，`gh api rate_limit`／`cortex doctor` 皆看不到，同時派 3 個 slice 即打爆，失敗訊息把使用者導向錯誤的處置（重新登入，token 其實完好）。
  - **新增 `paulsha_cortex/coordinator/spawn_admission.py`**：`SpawnAdmissionLimiter`（per-provider 最小啟動間隔，token-bucket 風格的 min-interval stagger，非併發上限、非序列化整個 job 生命週期）。`admit(provider)` 在真正 spawn 前呼叫一次，同一 provider 未跑滿最小間隔則等待補足差額，否則立即回傳；不同 provider 各自獨立時間軸，互不阻塞（不做全域序列化，避免吞吐倒退）；spawn 成功即視為釋放，不佔住後續長時間執行、無需對應 release()。Reservation 在鎖內原子完成、sleep 在鎖外執行，避免同 provider 並發呼叫互相踩。`resolve_provider()` 依優先序解出 bucket key：已解析的 model identity（`identity.executor`）＞呼叫端宣告的 executor 字面值＞launcher 自報的 `.executor` 屬性＞共用 `default` bucket。`clock`／`sleep` 皆可注入，供測試用假時鐘、不必真 wall-clock sleep。
  - **`spawn_admission=None` 在每一層都刻意解析為零間隔 no-op**（`resolve_limiter()`）：與過去「完全沒有這個參數」的行為等價，只有呼叫端顯式建構並注入 limiter 才會真的節流——避免既有 2180+ 個測試因為新增這個可選參數而意外背上真正的 wall-clock sleep（複驗過此設計無需假的模組級單例：production 唯一預設值只在 `manager_daemon.main()` 顯式建構一次，往下注入）。
  - **兩條 lane 接線**：`autonomy.dispatch_ready`（`autonomy.py:565-568` 新增 `limiter.admit(...)`，緊接在 launch 前）、`manager._dispatch_workflow_card`（`manager.py:6822-6823`）與其公開包裝 `manager.dispatch_workflow_card`／`manager.resume_workflow_run`（透過內部 `dispatch_or_stop` 轉發）皆新增可選 `spawn_admission` 參數。`manager_daemon.build_periodic_tick_runner` 對 workflow resume 迴圈（經 `_call_with_supported_kwargs` 遞交，向下相容既有 strict-signature fake）與 `run_tick_kwargs` 傳同一個 limiter instance，兩條 lane 因此共用同一份 per-provider 時間軸；`manager_daemon.build_request_executor`（手動 `cortex fanout`／`dispatch`／`tick` 請求——issue 的原始重現路徑）比照辦理。`manager_daemon.main()` 新增 `--spawn-min-interval-seconds`（預設讀 `PSC_SPAWN_MIN_INTERVAL_SECONDS`，未設則用內建 2 秒；亦支援 per-provider 覆寫 `PSC_SPAWN_MIN_INTERVAL_SECONDS__<PROVIDER>`，如 `..._COPILOT`），唯一建構真實 limiter 的地方，同一 instance 注入 `run_loop` 再分別餵給 request executor 與 periodic runner。
  - **`SubprocessLauncher` 新增公開唯讀屬性 `executor`**（`launcher.py`）：`resolve_provider()` 在沒有 per-slice identity 時，需要能從已注入的預設 launcher 自報實際 provider（原本只有私有 `_executor`）。
  - 29 個回歸測試（`tests/test_spawn_admission_limiter.py`）：limiter 本體（同 provider 錯開、不同 provider 不互相拖慢、per-provider 覆寫、reservation 語意、零間隔停用節流）、`resolve_provider`／`resolve_limiter`／`build_default_limiter`（含 env 解析與 malformed 值容錯）、以及兩條 lane 的實際接線（`dispatch_ready` 3 個同 provider slice 錯開／2 個不同 provider 不互相等待、`dispatch_workflow_card` 跨 run 同 provider 錯開、periodic tick 把同一 limiter instance 同時餵進 workflow resume 與 fanout run_tick）。修正前對這批接線測試實跑確認 RED（`build_periodic_tick_runner()`／`dispatch_workflow_card()`／`dispatch_ready()` 皆 `TypeError: got an unexpected keyword argument 'spawn_admission'`，5 failed / 24 passed，24 為不依賴接線的 limiter 本體測試）。全套 pytest：2209 passed、32 subtests passed（基線 2180/32，淨增 29），耗時與基線相當（無 real sleep 洩漏進既有測試）。
