### Added
- **交付後孤兒 run 的明確退休路徑 `cortex work retire-delivered`（Gap 1）**：當一個 work 的實際交付發生在 cortex 管線之外（例如 fallback 巷道用 subagent 直接做完並 merge），對應的 `WorkflowRun` 會卡在 `status=ongoing`／`current_phase=verify`／`facets=['needs_human']`，且它 build 階段建的 PR（記在 `pr_refs`）早已是 terminal（merged／closed）。既有 `cortex work abandon` 的 pre-delivery 閘門（`registry._manager_validate_workflow_abandon`：`current_phase==ship`、`pr_refs` 非空、ship step `gate_result==passed`、或 `completion_record_path` 非 None 任一即拒）使這種「有 pr_refs、PR 已 terminal」的孤兒無法退休，也無法 ship（candidate 常 dirty），形成狀態機死角。新增獨立、意圖明確的退休 work-action `retire-delivered`：**先透過既有 provider seam（`GitHubDeliveryClient.fetch_pr_lifecycle_status`，新增，走既有 `_api` 而非自 subprocess `gh`）驗證每個 `pr_ref` 的 PR 都為 terminal（merged 或 closed，任一未 terminal／malformed／跨 repo 即 fail-closed 拒絕）**，再把「已驗證 terminal」的結論落成 audit evidence（`~/.agents/coordinator/evidence/work-retire-delivered/<run_id>-<digest>.json`，schema `cortex-work-retire-delivered/v1`，內含每個 PR 的 terminal 狀態＋operator reason，比照既有 `work-abandon` 的 O_EXCL＋hardlink＋fsync＋0o444 immutable 寫入），最後才呼叫 registry 的 `_manager_retire_delivered_workflow_run` 將 run 標為 `superseded`。安全性依據：所有 PR 已 terminal ⇒ 沒有 in-flight delivery ⇒ 退休本地 run 安全。**刻意不弱化既有 `abandon` 的 pre-delivery 嚴格性**（新增 `test_abandon_still_refuses_any_pr_refs_run` 守衛：帶 pr_refs 的 run 仍被 abandon 拒絕）。registry 層維持純粹、不直接打 GitHub——PR-terminal 檢查放在 work-action 層（`work_actions.py`，已透過 `load_work_authority` 有 provider 存取），registry 的退休 admission 只要求 `ongoing`＋無 active job＋`pr_refs` 非空（delivered 簽名）。沿用既有 exact WorkflowRun CAS（`--expected-run-id`）＋bounded actor/reason，並具備 idempotent 重入（run 已 superseded 時從 durable evidence 重讀 terminal 證明、不再打 GitHub，故限流下重入仍成立）。CLI：`cortex work retire-delivered <work_id> --repo <owner/repo> --expected-run-id <run_id> --actor <name> --reason "<單行審計理由>"`（coordinator argparse choices 與 umbrella `_WORK_HELP` 同步）。

### Fixed
- **退休類 work-action 在 provider rate-limit 下不再硬失敗（Gap 2，#370 只保護了 resume 的延伸）**：`#370` 給 **resume** 加了 `_provider_rate_limit_result`，讓 authority 因 provider rate-limit degraded 時記 durable backoff、回軟結果、不 raise；但 **abandon／retire-delivered** 路徑沒有這層保護——`claim.load_work_authority`（經 `_authority_from_canonical_row`）在 canonical GitHub provider snapshot `status!="ok"` 且 diagnostics 帶 rate-limit 訊號時直接 raise `REASON_PROVIDER_RATE_LIMITED_CANONICAL`，結果正好在系統被限流、最需要清理 stuck run 時，退休操作也被擋死。`load_work_authority` 新增 opt-in 參數 `allow_rate_limited_last_known_good`（預設 `False`，逐層透傳至 `_authority_from_canonical_row`）：僅在「provider 因 rate-limit degraded **且** snapshot 仍留有先前成功的 last-known-good `revision`/`last_success_at`」的窄條件下，改用 last-known-good 續行建構 authority 而不 raise；退休不依賴 issue 的即時開關狀態，故此放行安全。`execute_work_action` 只對退休語境（`_RETIREMENT_ACTIONS = {abandon, retire-delivered}`）帶入此旗標，**claim/start 等需要即時 authority 的語境維持嚴格 fail-closed 預設**；其餘 degraded／缺 revision／壞 timestamp 的非 rate-limit 情境即使在退休語境下仍嚴格拒絕。
