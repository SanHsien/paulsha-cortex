### Added
- **Issue #384：LLM executor/provider 失敗缺 typed semantics、bounded recovery 與 policy-aware fallback**：新增 `paulsha_cortex/coordinator/provider_outcome.py`——把 executor CLI 失敗分類成 `auth`／`rate_limited`／`quota`／`transient`／`content`／`unknown` 六種 typed outcome，複用 #369 的 `executor_auth.classify_cli_output`（rate-limit 判定先於 login 判定）與 #370 的 `github_rate_limit.is_rate_limit_signal`/`is_auth_signal`，在其上疊 quota／transient／content 三類新訊號（刻意不重複收 "quota exceeded"／"usage limit"——兩者已被 rate-limit 正則收走，語意上都是「等時間窗過了就會恢復」）。新增中間 authority 等級 `SignalAuthority`（`structured` > `text_signal` > `hint`）解開 plan 內部矛盾：規則「stderr 關鍵字只做 hint 不升 authoritative」真正要擋的是「stderr 訊號不能升級到需要 structured authority 的動作（放寬 independence domain、永久拉黑 provider、略過人工複核）」，retry／re-route 從未要求 structured authority，故與 recovery matrix 期待 rate_limited 觸發 retry（copilot 限流只有 stderr 文字、無 structured code）不衝突——`TEXT_SIGNAL` 等級即可驅動 bounded、可逆的 retry/re-route，`HINT` 等級（無訊號匹配）永不驅動任何自動決策。

### Fixed
- **同上（#384）：`Dispatcher._finalize_headless`（`dispatcher.py:205-223`）、`registry.update_headless_result`（`registry.py:977-1012`）**：headless job 判定 `status=="failed"` 時讀 log 尾端（新增 `provider_outcome.read_log_tail`，有界讀取，避免大檔 I/O 成本）分類一次，寫回 job registry 新欄位 `provider_outcome`（`{outcome, authority, reason, retryable}`，`_validate_loaded_job` 新增對應 schema 檢查，舊狀態檔缺此欄位視為 `None`，向後相容）。這是唯一的分類發生點，slice lane／workflow lane 共用同一份結果，不各自重新解析 log。
- **Slice lane（`manager.py` 的 `complete_tick`，build-phase failure 分支，舊行號 1750-1757 附近，行號因多次 merge 漂移）**：不再一律把 build-phase failure 壓平成寫死的 `"builder-failed"`——`job["provider_outcome"]` 有分類時 `gate_reason` 併入 outcome（如 `"builder-failed-rate_limited"`），並把完整分類寫進 handoff manifest 的新欄位 `provider_outcome`，供 `slice_status_entry` 投影回 `cortex inspect status` 的 `attention` 清單。Slice lane 沒有 workflow lane 的 `run.attempts` 可持久化 retry 計數，故本 lane 只做分類與可觀測性，不做 bounded auto-retry（沿用既有 operator `retry-build` 手動復原路徑，範圍界定）。
- **Workflow lane（`resume_workflow_run` 的 job-failed 分支，舊行號 6863-6886 附近）**：不再一律把任何失敗壓平成 `"job-failed"`＋`needs_human`。
  - **typed 分類**：有分類時 `reason` 併入 outcome（`"job-failed-{outcome}"`），並回報 `provider_outcome`／`provider_outcome_authority`；沙箱 drift（reviewer 動過 candidate）時刻意不看分類、不重試，維持既有 `"reviewer-candidate-drift"` fail-closed 路徑。
  - **bounded durable retry**：比照既有 schema-retry 樣板（同一函式內，`_malformed_workflow_card_terminal` 分支）——新增 `terminal_contract.MAX_PROVIDER_RETRIES = 2`（與 `MAX_SCHEMA_RETRIES` 分開命名計數，兩種重試性質不同、逾限 reason 也不同）、`manager._provider_retry_attempt_key(card_id)`（`run.attempts` 上的 `provider-retry:<card>` 鍵，複用既有 state store，不新增）。只有 outcome ∈ `{rate_limited, transient}`（`ProviderOutcome`／`RETRYABLE_OUTCOMES`）且 authority 非 `hint` 才重試；`auth`／`content`／`quota`／`unknown` 直接 needs_human，不盲目重試。逾限（`seen >= MAX_PROVIDER_RETRIES`）轉 `"provider-retry-exhausted"`。raw evidence 沿用既有 `terminal_diagnostics`（`_terminal_parse_diagnostics`），未新增診斷通道。
  - **policy-aware re-route（不放寬 independence domain）**：新增 `manager._provider_failure_reroute`，複用 `runtime_preflight.evaluate_dispatch_gate`（#369 已把 provider snapshot 接進生產的同一套機制）——把「剛觀察到的這次失敗」餵成一筆僅本次呼叫可見、in-memory 的 provider snapshot（`provider_prober=None`，不觸發真實 CLI 探測子行程、不寫入任何 durable snapshot、不碰 `_EXECUTOR_AUTH_CACHE`），讓 gate 在 `_workflow_identity_candidates`（既有 domain-filtered 順序，**完全未改動**）上跳過剛失敗的 identity、選下一個候選。`_dispatch_workflow_card`／`dispatch_workflow_card` 新增 `forced_identity` 參數（提供時略過 `_runtime_preflight_gate`，直接用這個已算好的 identity，不重跑一次探測）。只剩失敗中的那個 identity 合格時（`evaluate_dispatch_gate` 回 `needs_human`）helper 回 `None`，呼叫端退回既有 `_select_workflow_identity`——仍會選中同一個 identity（唯一合法選擇），不是 bug；reviewer 候選清單本就依 independence domain 排除跟 builder 同 domain 的 identity，`_provider_failure_reroute` 只在這份既有清單上選人，結構上不可能 policy-shopping（例如 Codex builder 失敗後不會讓 Codex 又跑去當 reviewer）。
- **`porcelain/inspect.py` 的 `_run_status`**：`--json` 已透過 `slice_status_entry` 的 `provider_outcome` 欄位 passthrough；文字模式 `_print_status` 新增一行摘要（比照 #372 的 attention 修法），不必展開整包 JSON 就能看出是哪個 slice、哪一種 outcome、可不可 retry。

### 複驗更正（見 issue #384 2026-08-10 comment，已依此調整實作範圍）
1. 「壓平」原描述「很容易被壓平」更正為「一律壓平」（無任何分類分支）。
2. 接線既有型別而非新造：複用 `runtime_preflight.ProviderFreshness`／`ProbeBudget`／`PreflightOutcome.PROVIDER_UNAVAILABLE`／`evaluate_dispatch_gate` 的 re-route 機制（#369 已接進生產），未新造平行的 provider health 型別體系。刻意不觸碰 `_EXECUTOR_AUTH_CACHE` 或幫任何 card 新增 `provider:executor` 宣告——production `cards.yaml` 目前尚未宣告任何 `provider:executor`（既有註解：要接上前須先確認 CI／各執行環境對 claude／codex／copilot CLI 的可得性，避免 dispatch 熱路徑意外 spawn 子行程），本票的 re-route 是 retry 專屬、in-memory、一次性的決策輸入，不改變一般 dispatch 熱路徑的行為。
3. Policy-shopping 防線落實為結構性保證（`_provider_failure_reroute` 完全複用 `_workflow_identity_candidates` 既有 domain-filtered 清單，不新增放寬邏輯），而非只是 forward-looking 文件約束。
